# Spec-Driven Development Lifecycle Specification

## Purpose

Defines the overall spec-driven development (SDD) lifecycle — the linear flow from intent to implementation that every change follows. This is the methodology spec that governs how PFB, EAD, implementation plan, and spec-graph work together.

## Requirements

### Requirement: Linear artifact flow

The SDD lifecycle SHALL follow a strict linear sequence: PFB → Specs → EAD → Implementation Plan → Implement. Each artifact MUST be complete before the next can begin. No artifact SHALL be created out of order.

#### Scenario: Normal flow

- **WHEN** a developer wants to implement a new feature
- **THEN** the workflow SHALL proceed: write the PFB (why + scope), write the specs (what changes), write the EAD (how to build it), generate the implementation plan (steps), then execute the plan

#### Scenario: Skipping an artifact

- **WHEN** a developer attempts to create an EAD without specs
- **THEN** the system SHALL block the EAD creation and report that specs are required first

### Requirement: Artifact dependency chain

Each artifact in the SDD flow SHALL depend on and reference its predecessors. The PFB is the root. Specs reference the PFB. The EAD references both the PFB and specs. The implementation plan references all three.

#### Scenario: Traceability chain

- **WHEN** a reviewer reads an implementation plan task
- **THEN** they SHALL be able to trace it back to a design decision in the EAD, a requirement in the specs, and the original intent in the PFB

### Requirement: Change as the unit of work

A change is the atomic unit of the SDD lifecycle. Each change SHALL have exactly one PFB, one set of specs (one or more capability specs), one EAD, and one implementation plan. A change MUST be scoped small enough to implement in a bounded number of sessions.

#### Scenario: Well-scoped change

- **WHEN** a change has a PFB with clear scope boundaries, specs with testable scenarios, and an EAD with concrete decisions
- **THEN** the implementation plan SHOULD contain no more than 50 tasks grouped into logical phases

#### Scenario: Change too large

- **WHEN** a change's implementation plan exceeds 50 tasks or spans more than 5 independent subsystems
- **THEN** the change SHOULD be split into multiple smaller changes with explicit dependencies in the spec-graph

### Requirement: Brownfield-first approach

The SDD lifecycle SHALL support brownfield development (existing codebases) as the primary use case. The PFB and EAD MUST account for existing code, constraints, and migration concerns — not just greenfield design.

#### Scenario: Existing codebase

- **WHEN** a change targets a repo with existing code
- **THEN** the PFB SHALL document current state and constraints, and the EAD SHALL address migration, backwards compatibility, and rollback

### Requirement: Human review gates

The SDD lifecycle SHALL include human review as a gate between each artifact phase. Artifacts MAY be generated by AI agents, but MUST be reviewed and approved before the next phase begins. No autonomous cascade from PFB to implementation without human checkpoints.

#### Scenario: AI-generated artifact review

- **WHEN** an AI agent generates an EAD from a PFB and specs
- **THEN** the EAD SHALL be marked as draft until a human reviews and approves it
- **AND** the implementation plan SHALL NOT be generated until the EAD is approved
